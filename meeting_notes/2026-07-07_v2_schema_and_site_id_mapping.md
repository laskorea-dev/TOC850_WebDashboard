# 회의록: Supabase V2 신규 스키마 설계 및 지점 식별자 직접 매립 아키텍처 도입 (2026-07-07)

## 2. 기존 아키텍처의 한계 및 문제점
* 기존 구조(v4.3 이하)에서는 계측기 데이터가 업로드될 때 컴퓨터 이름 등의 물리 기기 ID(`Device_ID`)에 전적으로 의존하였습니다.
* 이 방식은 현장에서 컴퓨터가 고장 나거나 다른 사유로 장비 PC가 교체되어 `Device_ID`가 달라질 때, 웹 대시보드에서 과거 데이터와 신규 데이터가 동일한 지점명(`?site=지점명`) 아래서 매끄럽게 합쳐지지 않고 단절되는 중대한 관리적 애로사항이 있었습니다.

## 3. 합의 및 결정 사항
기존 컬럼/테이블 제약 조건에 얽매이지 않고, 데이터 무결성 및 연속성을 완벽히 구현하기 위해 **Supabase V2 통합 설계**를 도입하기로 합의하였습니다.

1. **V2 스키마 설계**:
   * 지점 설정 관리를 위한 독립 테이블인 `site_config_v2`를 신설합니다.
   * 통합 계측 로그 기록을 위한 독립 테이블인 `measure_logs_v2`를 신설하고, 테이블 내에 **지점 식별자(`Site_ID`)**와 **물리 기기 식별자(`Device_ID`)** 컬럼을 동시에 수용하도록 설계합니다.
2. **지점과 장치의 역할 분리 (Option 2 채택)**:
   * **`Device_ID`**는 물리적인 컴퓨터 장치명을 식별하는 로그 용도로만 활용하고, 차트 쿼리 및 데이터 연속성의 키는 **`Site_ID` (지점 코드)**가 담당합니다.
   * 웹 대시보드(차트, CSV 다운로드, 모의 데이터 셋 등)는 기본적으로 `Site_ID = eq.Samyang_Incheon` 조건으로 데이터를 쿼리합니다.
   * 이로 인해 장치가 교체되더라도 설정 파일의 `site_id`만 이전 지점명과 일치시켜 주면 과거 데이터와 새 데이터가 하나의 타임라인에 끊김 없이 연결되어 출력됩니다.
3. **Zero-Touch Onboarding 유지**:
   * 미결정/테스트 단계 PC는 설정파일에 `"site_id": "auto"`로 구성하여, PC 부팅 시 컴퓨터 호스트명을 `Site_ID`로 채택해 Supabase 상에 즉각적인 테스트가 가능하게 합니다.
