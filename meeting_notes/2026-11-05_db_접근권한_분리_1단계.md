인계 문서 §1.3 의 계획에서 어긋난 점:

- 조회 전용으로 바꾸면 고객용 대시보드의 쓰기가 막힌다. 설정 저장, 수신인 등록·삭제, 모의 데이터 입력·삭제를 브라우저에서 직접 했다.
- 교체 대상에 테스트 배포가 빠져 있었다.
- §1.3 의 DELETE 검증은 믿기 어렵다. RLS 로 막혀도 0행 204 가 나올 수 있으므로 `pg_policies` 와 권한 조회로 확인한다.

- 못 한 것: 실제 Vercel·Supabase 에서의 API 동작, 화면에서의 저장 동작, anon 키 조회. 로컬 `vite` 에는 `/api` 가 없다.

## 4. 적용 순서 (순서를 바꾸면 화면이나 저장이 깨진다)

1. **003 SQL 실행** — 2026-11-05 적용 완료. 콘솔에서 정책 2건 확인.
2. **서버 환경변수 확인**: 고객용 Vercel 에 `SUPABASE_URL`·`SUPABASE_KEY` 가 이미 있어(7/8 등록) 추가 입력이 필요 없다. 쓰기 API 는 기존 API 와 같이 이 값을 읽는다.
3. **브랜치 배포 후 실제 저장 확인.** 프리뷰에서 시험 지점으로 설정 저장·모의 데이터를 확인하고 `main` 에 병합한다.
4. **3곳의 `VITE_SUPABASE_KEY` 를 anon 으로 교체하고 재배포.** 사무실용은 조회만 하므로 코드 변경이 없다.
   - 테스트 배포는 CLI 수동 배포이고 경보·텔레그램이 이 주소를 쓴다. 현재 프로덕션의 소스 버전을 먼저 확인하고, 재배포 뒤 `/api/send-alert` 응답과 텔레그램 등록을 확인한다.
5. **검증**: 번들 role 이 anon 인지, 화면 조회·저장이 되는지, `pg_policies` 와 권한이 의도대로인지 본다.

## 5. 이 단계로 막히지 않는 것

- **이미 유출된 service_role 키는 계속 유효하다.** 재발급은 현장 업로더 갱신이 필요해 이번 범위 밖이다. 이 단계는 키가 새 번들에 실리는 것을 멈출 뿐이다.
- anon 으로도 `device_config.passcode` 와 `toc_alert_high.telegram_bot_token` 이 읽힌다. 접속 화면이 브라우저에서 패스코드를 대조하고, 사무실용도 passcode 를 조회하기 때문이다. 패스코드가 읽히면 쓰기 API 인증도 통과할 수 있으므로 서버 검증으로 옮기는 후속 작업이 필요하다.
- 쓰기 API 에 시도 횟수 제한이 없고 기본 패스코드(`850`)가 약하다.
- Security Definer 뷰 3개는 그대로다. 측정 데이터 조회만 가능하다.
