- 조회 전용으로 바꾸면 고객용 대시보드의 쓰기가 막힌다. 설정 저장, 수신인 등록·삭제, 모의 데이터 입력·삭제를 브라우저에서 직접 했다.

## 2. 적용한 것

- `tools/migrations/003_dashboard_read_only.sql`: 프로덕션 적용. anon 조회 정책, anon·authenticated 쓰기 권한 회수.
- `dashboard/api/dashboard-write.js`: 쓰기 전용 서버 API. 요청마다 패스코드를 서버에서 대조하고 정해진 action·컬럼만 처리한다. 서버 키는 기존 `SUPABASE_KEY`.
- `dashboard/src/App.jsx`: 쓰기 5곳을 이 API 로 전환. 패스코드를 바꾸면 이후 요청은 새 값으로 인증한다.
- `dashboard/tests/dashboard-write.test.mjs`: API 시험 18건(`npm test`).
- Vercel `VITE_SUPABASE_KEY` (고객용·사무실용): Publishable 키. Type 은 **Config** 여야 한다. Secret 은 `VITE_` 이름 때문에 저장이 거부되고, 저장된 Secret 은 Config 로 못 바꿔 지우고 새로 만들었다.
- 로컬 `dashboard/.env.local`, 사무실용 `.env`·`.env.production.local`·`.vercel/.env.production.local` 도 교체. 옛 값이 남으면 수동 배포 때 다시 실린다.

anon 대신 Publishable 키를 고른 이유: 콘솔이 기존 키 방식을 2027년 초 폐지한다고 안내한다. `apikey` 와 `Authorization: Bearer` 를 함께 보내는 현재 코드에서 동작을 실측했다.

## 4. 되돌리기

Vercel 의 키 값을 되돌리고 재배포한다. 정책은 003 머리말의 `drop policy`. 쓰기 권한 회수는 Supabase 기본 grant 를 다시 주어야 하지만, 업로더·서버 API 는 service_role 이라 필요 없다.

## 5. 이 단계로 막히지 않는 것

- **이미 유출된 service_role 키는 계속 유효하다.** 재발급은 현장 업로더 갱신이 필요해 이번 범위 밖이다. 이 단계는 키가 새 번들에 실리는 것을 멈출 뿐이다.
- **테스트 배포(`dashboard-ochre-two-35`, 7/21 CLI 배포) 번들에 service_role 이 남아 있다.** 경보·텔레그램 경로라 건드리지 않았다.
- **기존 키 방식 폐지(2027년 초 안내)** 전에 업로더 키를 교체해야 한다.
- anon 으로도 `device_config.passcode` 와 `toc_alert_high.telegram_bot_token` 이 읽힌다. 접속 화면이 브라우저에서 패스코드를 대조하고, 사무실용도 passcode 를 조회하기 때문이다. 패스코드가 읽히면 쓰기 API 인증도 통과할 수 있으므로 서버 검증으로 옮기는 후속 작업이 필요하다.
- 쓰기 API 에 시도 횟수 제한이 없고 기본 패스코드(`850`)가 약하다.
- Security Definer 뷰 3개는 그대로다. 측정 데이터 조회만 가능하다.
