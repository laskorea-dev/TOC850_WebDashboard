## 1. [P1] service_role 키 공개 노출

### 1.1 확인된 사실

두 개의 배포된 프론트엔드 번들 **모두**에 `role: "service_role"` JWT가 포함되어 있습니다. 2026-09-10 직접 확인.

| 앱 | URL | 접근 통제 | 번들 내 키 |
|---|---|---|---|
| 메인 대시보드 | `toc-850-web-dashboard.vercel.app` | **없음** (고객사 배포 URL) | service_role |
| 오피스 대시보드 | `toc-office-dashboard.vercel.app` | 클라이언트 암호 게이트 | service_role |

재현 방법 (암호 불필요):

```bash
IDX=$(curl -s https://toc-850-web-dashboard.vercel.app/ | grep -oE '/assets/index-[A-Za-z0-9_-]+\.js' | head -1)
curl -s "https://toc-850-web-dashboard.vercel.app$IDX" \
  | grep -oE 'eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+' | head -1
# 페이로드를 base64 디코딩하면 role 클레임 확인 가능
```

**노출 출처 (2026-09-10 확인)** — 양쪽 모두 환경변수에 anon이 아닌 service_role이 들어가 있음:

| 파일 | 변수 | 실제 role |
|---|---|---|
| `db_upload_and_dashboard/dashboard/.env.local` | `VITE_SUPABASE_KEY` | service_role |
| `toc850_office_dashboard/.env` | `VITE_SUPABASE_KEY` | service_role |
| `toc850_office_dashboard/.env.production.local` | `VITE_SUPABASE_KEY` | service_role |

`VITE_` 접두사가 붙은 값은 빌드 시 클라이언트 번들에 그대로 인라인됩니다. **운영 정본은 Vercel 환경변수이므로 Vercel 쪽도 반드시 함께 확인·교체해야 합니다.**

부수 사항:
- 오피스 대시보드의 접속 암호(`VITE_OFFICE_PASSCODE`, 운영값 `las-toc-2026`)도 번들에 **평문 상수**로 존재. 암호 게이트는 화면만 가릴 뿐 번들 취득을 막지 못함.
- NAS 동기화가 `.env`를 포함해 백업하므로 **NAS에도 같은 키가 평문으로 존재**합니다(§4). NAS 폴더 권한이 개발부로 제한되어 있는지 확인 필요.
- 오피스 대시보드 화면 하단에 "Supabase에 **읽기 전용**으로 조회합니다"라는 문구가 있으나, service_role 키로는 사실이 아님. 문구도 함께 수정 필요.
- `dashboard/.env.local`의 `VITE_SUPABASE_KEY`가 anon이 아닌 service_role. `dashboard/.env.example`에는 "service_role 절대 금지"라고 명시되어 있어 **문서와 실제 설정이 어긋난 상태**.
- `3_히스토리_및_완료보고서.md` 2026-07-27 항목에 service_role 키를 git 히스토리에서 제거하면서 "자격 증명 재발급은 후속 과제로 등록"이라고 기록됨. **그 재발급이 미완료 상태로 보임.**

### 1.2 영향 범위

service_role은 RLS를 전면 우회합니다. URL을 아는 누구나:

- `measure_logs_v2`, `device_config` 전체 조회
- **임의 수정 / 전체 삭제**
- 신규 행 삽입 (허위 측정값 주입)

데이터 민감도가 낮더라도 **측정 이력 전량 소실**이 실질적 위험입니다.

### 1.3 1단계 — 봉쇄 (현장 PC 무관, 즉시 가능)

목적: 이미 유출된 키를 무효화하지는 못하지만, **공개 번들로 계속 배포되는 것을 중단**합니다.

1. Supabase 콘솔에서 **anon(public) 키** 확인
2. Vercel 두 프로젝트의 `VITE_SUPABASE_KEY`를 anon 키로 교체 후 재배포
   - `toc-850-web-dashboard`
   - `toc-office-dashboard` (별도 저장소 — §4.1 참조)
3. **동시에** Supabase에서 RLS 활성화 + 조회 전용 정책 추가

> ⚠️ **2와 3은 반드시 함께 수행할 것.** RLS가 꺼진 상태에서 anon 키로만 바꾸면 anon 키로도 쓰기·삭제가 가능하므로 아무 효과가 없습니다.

업로더는 자기 `uploader_config.json`의 service_role 키를 계속 사용하므로 RLS를 우회합니다. **전송 동작에 영향 없음 — 현장 방문 불필요.**

RLS 정책 초안 (SQL Editor에서 실행, 적용 전 검토 필요):

```sql
alter table public.measure_logs_v2 enable row level security;
alter table public.device_config   enable row level security;

-- 대시보드(anon)는 조회만 허용
create policy "anon read measure_logs_v2"
  on public.measure_logs_v2 for select to anon using (true);

create policy "anon read device_config"
  on public.device_config for select to anon using (true);

-- INSERT/UPDATE/DELETE 정책은 만들지 않는다.
-- 업로더는 service_role 이므로 RLS 를 우회하여 계속 쓰기 가능.
```

검증 (적용 후, anon 키로 실행 — 0건 매칭이라 데이터 변경 없음):

```bash
KEY=<anon key>
B=https://abfjmqnurtjfbflquqsp.supabase.co/rest/v1
# 조회는 200 이어야 함
curl -s -o /dev/null -w "SELECT %{http_code}\n" -H "apikey: $KEY" -H "Authorization: Bearer $KEY" \
  "$B/measure_logs_v2?select=Date_Time&limit=1"
# 삭제는 401/403 이어야 함 (204 가 나오면 RLS 미적용 — 실패)
curl -s -o /dev/null -w "DELETE %{http_code}\n" -X DELETE -H "apikey: $KEY" -H "Authorization: Bearer $KEY" \
  "$B/measure_logs_v2?Date_Time=eq.1900-01-01T00:00:00"
```

레거시 JWT 방식이므로 **JWT 시크릿 갱신 시 anon과 service_role이 동시에 무효화**됩니다. 아래 순서를 지키지 않으면 업로더가 원격 업데이트 지시를 받을 통로 자체를 잃습니다.

### 2.2 원인

**오피스 대시보드(`toc-office-dashboard`)의 자동순환입니다.** 메인 대시보드가 아닙니다.

- 실측 요청량: **시간당 1,262건 = 분당 21건**
- → **순환 1스텝당 Supabase 요청 약 1건**. 설계상 폴링 주기(60초, 번들 상수 `Dt=6e4`)의 약 20배.

응답 자체는 이미 작습니다 (gzip 후 실측):

| 요청 | 크기 |
|---|---|
| 6시간 전체 지점 조회 | 643 B |
| device_config 전체 | 584 B |
| 지점별 7일 이력 | 4,724 B |
| 증분 조회 (신규 0건) | 2 B |

문제는 크기가 아니라 **횟수**입니다. 참고로 실제 데이터 유입량은 **하루 142건**(업로더 주기 900초)에 불과합니다.

## 부록: 재사용 가능한 측정 명령

egress 일별 실측값은 Supabase 대시보드 차트의 React fiber에서 바이트 단위로 추출 가능 (조직 usage 페이지에서 실행):

```js
const w=[...document.querySelectorAll('.recharts-wrapper')];
let data=null;
for(const el of w){
  const k=Object.keys(el).find(k=>k.startsWith('__reactFiber$'));
  let f=el[k],d=0;
  while(f&&d<40){
    const p=f.memoizedProps;
    if(p&&Array.isArray(p.data)&&p.data[0]&&'egress' in p.data[0]){data=p.data;break;}
    f=f.return;d++;
  }
  if(data)break;
}
data.map(r=>[r.period_start,r.egress]);
```

요청 수는 프로젝트 → Observability → API Gateway 에서 확인. 요청별 경로는 Logs → Edge Logs.
